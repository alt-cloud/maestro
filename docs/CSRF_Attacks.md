Атака **CSRF (Cross-Site Request Forgery / Межсайтовая подделка запроса)** традиционно ассоциируется с классическими веб-приложениями, однако она представляет собой серьезную угрозу и для **API интерфейсов** (REST, GraphQL, gRPC-Web), особенно если эти API используются браузерными клиентами (Single Page Applications — SPA, или традиционными веб-фронтендами).

Ниже представлено подробное описание того, как работает CSRF в контексте API, какие условия необходимы для атаки и как от нее защищаться.

---

### 1. Суть уязвимости в контексте API
CSRF — это атака, при которой злоумышленник заставляет браузер аутентифицированного пользователя выполнить нежелательный запрос к целевому API. 

Ключевая особенность браузеров заключается в том, что они **автоматически добавляют cookie-файлы** (включая сессионные токены) к каждому запросу на домен, которому эти cookie принадлежат. Если API использует cookie для аутентификации и не имеет дополнительных механизмов проверки происхождения запроса, он выполнит команду злоумышленника, считая её легитимным действием пользователя.

*Важное уточнение:* CSRF актуальна **только для API, к которым обращаются из браузера**. Мобильные приложения, десктопные клиенты или серверные интеграции (backend-to-backend) не подвержены CSRF, так как они не используют автоматическую подстановку cookie браузером.

---

### 2. Анатомия атаки на API (Пошаговый механизм)

1. **Аутентификация:** Пользователь заходит в свой аккаунт на сайте `bank.com`. Фронтенд (SPA) отправляет логин и пароль на `api.bank.com/auth/login`. Сервер возвращает сессионную cookie (например, `SESSIONID=abc123`) с флагом `HttpOnly`.
2. **Переход на сайт злоумышленника:** Не закрывая вкладку с `bank.com`, пользователь переходит на фишинговый сайт `evil.com`.
3. **Инициация атаки:** На `evil.com` загружается скрытый JavaScript-код или HTML-форма, которая формирует запрос к `api.bank.com/api/transfer` (например, для перевода средств).
4. **Автоматическая подстановка:** Браузер пользователя отправляет запрос на `api.bank.com`. Поскольку домен совпадает, браузер автоматически прикрепляет cookie `SESSIONID=abc123`.
5. **Выполнение:** API `bank.com` получает запрос, видит валидную сессионную cookie и выполняет операцию перевода, так как не может отличить этот запрос от запроса, инициированного самим сайтом `bank.com`.

---

### 3. Особенности атаки на современные REST и JSON API

Традиционные CSRF-атаки использовали HTML-формы (`application/x-www-form-urlencoded` или `multipart/form-data`). Современные API обычно ожидают данные в формате **JSON** (`application/json`). 

Казалось бы, HTML-форма не может отправить JSON, и API защищено. Но злоумышленники используют следующие обходные пути:

#### А. Игнорирование Content-Type на бэкенде
Многие фреймворки (например, Express.js, Spring, Django) при определенных настройках могут парсить тело запроса как JSON, даже если заголовок `Content-Type` отсутствует или имеет значение `text/plain`. Злоумышленник может отправить JSON-подобную строку через форму с `enctype="text/plain"`.

#### Б. Использование Fetch / XMLHttpRequest и CORS
Злоумышленник может использовать JavaScript (`fetch` или `XMLHttpRequest`) для отправки настоящего JSON-запроса. 
Здесь вступает в игру **CORS (Cross-Origin Resource Sharing)**:
* Если API отправляет JSON, браузер отправляет **Preflight-запрос (OPTIONS)**.
* Если на API **неправильно настроен CORS** (например, сервер возвращает `Access-Control-Allow-Origin: *` или динамически отражает домен злоумышленника, и при этом разрешает credentials), браузер пропустит запрос, и CSRF-атака пройдет.
* Если API принимает простые запросы (Simple Requests) без Preflight, но при этом уязвим к подделке Content-Type (см. пункт А), защита также обходится.

#### В. GraphQL API
В GraphQL CSRF-атаки направлены на выполнение **мутаций** (mutations). Если мутация не имеет защиты, злоумышленник может отправить POST-запрос с GraphQL-запросом в теле, используя те же методы обхода Content-Type или через уязвимости CORS.

---

### 4. Пример вредоносного кода (Сценарий атаки)

Допустим, API принимает переводы в формате JSON на эндпоинт `POST /api/v1/transfer`.

**Вариант 1: Обход через text/plain (если бэкенд парсит тело независимо от заголовка)**
```html
<!-- Скрытая форма на сайте злоумышленника -->
<form action="https://api.bank.com/api/v1/transfer" method="POST" enctype="text/plain">
    <input name='{"amount":1000,"to":"attacker_account","ignore_me":"' value='dummy"}' type="hidden">
    <input type="submit" value="Click me!">
</form>
<!-- Тело запроса будет выглядеть как валидный JSON, если бэкенд не проверяет Content-Type строго -->
```

**Вариант 2: Использование Fetch (если CORS настроен небезопасно)**
```javascript
// Скрипт на сайте evil.com
fetch('https://api.bank.com/api/v1/transfer', {
    method: 'POST',
    credentials: 'include', // Обязательный параметр для отправки cookie
    headers: {
        'Content-Type': 'application/json'
    },
    body: JSON.stringify({
        amount: 1000,
        to: 'attacker_account'
    })
});
```

### 5. Методы защиты API от CSRF

Защита API от CSRF строится на принципе **явного подтверждения намерений** пользователя или **блокировки автоматической отправки учетных данных**.

#### 1. Использование Bearer-токенов (Лучшая практика для SPA)
Вместо cookie, используйте токены (JWT, OAuth 2.0 Access Tokens), которые передаются в заголовке `Authorization: Bearer <token>`.
* **Почему это работает:** Браузеры не умеют автоматически добавлять заголовок `Authorization`. Злоумышленник не может заставить браузер отправить этот заголовок через HTML-форму или простой кросс-доменный запрос.
* *Нюанс:* Токен нужно где-то хранить. Если хранить его в `localStorage`, приложение становится уязвимым к XSS. Если в `sessionStorage` — токен теряется при закрытии вкладки. Компромиссом является хранение токена в памяти (RAM) JavaScript с использованием Refresh Token Rotation и HttpOnly cookie только для refresh-токена (который, в свою очередь, нужно защищать от CSRF).

#### 2. Атрибут SameSite для Cookie
Если API использует cookie для аутентификации, установите атрибут `SameSite=Strict` или `SameSite=Lax`.
* **Strict:** Cookie не отправляются вообще ни в каких кросс-доменных запросах. (Максимальная защита, но может сломать UX, если пользователь переходит по ссылке из email/мессенджера).
* **Lax:** Cookie отправляются только при навигации верхнего уровня (GET-запросы при переходе по ссылке). POST-запросы от третьих лиц блокируются. Это современный стандарт защиты по умолчанию во всех браузерах.

#### 3. Требование кастомных заголовков (Custom Headers)
Заставьте API требовать наличия специфического заголовка, например, `X-Requested-With: XMLHttpRequest` или `X-CSRF-Token: 1`.
* **Почему это работает:** Браузер не добавит этот заголовок автоматически. А кросс-доменный запрос с кастомным заголовком вызовет **CORS Preflight (OPTIONS)**. Если CORS настроен правильно (запрещает домен злоумышленника), браузер даже не отправит основной POST-запрос.

#### 4. Строгая проверка Content-Type
API должен жестко отвергать любые запросы, у которых `Content-Type` не равен `application/json` (или `application/graphql`). Это предотвратит атаки с использованием HTML-форм и `text/plain`.

#### 5. Паттерн "Double Submit Cookie" (Anti-CSRF Token)
Если по каким-то причинам нельзя использовать SameSite или кастомные заголовки:
1. Сервер генерирует уникальный CSRF-токен и отдает его фронтенду (например, в cookie `XSRF-TOKEN` без флага `HttpOnly`, чтобы JS мог его прочитать).
2. Фронтенд (SPA) при каждом мутирующем запросе (POST/PUT/DELETE) читает эту cookie и добавляет её значение в кастомный заголовок `X-XSRF-TOKEN`.
3. API сравнивает значение в cookie и в заголовке. Злоумышленник с другого домена не сможет прочитать cookie (из-за Same-Origin Policy) и, следовательно, не сможет сформировать правильный заголовок.

#### 6. Проверка заголовка Origin / Referer
API может проверять заголовки `Origin` или `Referer`. Если запрос приходит с домена, который не входит в белый список (whitelist), API должен его отклонить. (Этот метод хорош как дополнительная линия обороны, но не как единственная, так как в некоторых корпоративных сетях или из-за настроек приватности эти заголовки могут отсутствовать).

#### 7. Step-up Authentication (Повышенная аутентификация)
Для критически важных операций API может требовать повторного ввода пароля, PIN-кода или подтверждения через 2FA/MFA. Это полностью исключает возможность незаметного выполнения действия через CSRF.

### Резюме
Для современных API, обслуживающих браузерные клиенты, **наиболее надежной архитектурой защиты** является отказ от сессионных cookie в пользу Bearer-токенов в заголовке `Authorization`, либо использование cookie с атрибутом `SameSite=Lax/Strict` в сочетании со строгой проверкой `Content-Type: application/json` и правильными настройками CORS.
